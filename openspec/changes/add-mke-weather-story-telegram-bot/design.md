## Context

This is a new service with no existing application or infrastructure baseline. See [proposal.md](proposal.md) for motivation and the delta specifications for behavioral requirements. It needs scheduled execution, configurable NWS offices, external calls to NWS and Telegram, strict duplicate prevention, durable story and image records, and private operator alerting with a secondary email path.

The source of truth will be a public GitHub repository. GitHub is also the controlled entry point for validation, dependency maintenance, release creation, and promotion requests; AWS remains the runtime and infrastructure control plane.

## Goals / Non-Goals

**Goals:**

- Run a low-operations AWS workload every 15 minutes.
- Make office selection configuration-driven so the implementation can expand beyond MKX without redesigning the ingestion contract; enable only MKX initially.
- Maintain immutable publication-attempt records with at most one automatic Telegram send attempt per reservation; do not claim exactly-once external delivery.
- Retain downloaded image bytes and queryable metadata with the story history.
- Keep bot credentials out of code, SAM outputs, and logs.
- Notify the operator by SNS/email if private Telegram alert delivery fails.
- Make every deployable artifact traceable to a reviewed Git commit, dependency lock, security/cost evidence, and release identity.
- Protect public collaboration and delivery surfaces against accidental secret disclosure and unreviewed production changes.

**Non-Goals:**

- Backfill historical NWS stories or provide an end-user analytics UI.
- Enable or implement offices other than MKX in this change.
- Guarantee exactly-once delivery confirmation from Telegram; Telegram does not expose an idempotency key, so ambiguous network outcomes are treated conservatively to protect the no-duplicates requirement.
- Use SQS for polling, publication, or alert delivery.
- Treat GitHub Releases as a substitute for CloudFormation change sets or production approvals.

## Decisions

### AWS SAM on CloudFormation with EventBridge Scheduler

Use an AWS SAM template (`Transform: AWS::Serverless-2016-10-31`) deployed by CloudFormation. SAM keeps Lambda packaging, permissions, and event wiring concise while permitting ordinary CloudFormation resources for EventBridge Scheduler, DynamoDB, S3, CloudWatch, Secrets Manager, SNS, and IAM. Configure one `ScheduleV2`/EventBridge Scheduler schedule for each active office using `rate(15 minutes)`, UTC, `FlexibleTimeWindow: OFF`, an explicit Scheduler execution role, `MaximumRetryAttempts: 0`, maximum event age of 60 seconds, and an input payload containing exactly the active office ID. Each target invokes the publisher Lambda for only that office; invocations do not batch offices. Configure the publisher Lambda explicitly with a 900-second timeout and 1024 MB memory, then tune memory from production duration and maximum-memory metrics. Pass a registry seeded with all NWS offices, with only MKX active for MVP.

Scheduler retries are intentionally disabled. A failed invocation waits for the next scheduled poll; publication retries are governed by the DynamoDB attempt state machine. Permitted `429` and explicit `5xx` retries may occur in the same run through new reservations, while controlled deferrals return to the next poll. If a Lambda timeout occurs after Telegram may have accepted a message, the next run detects the stale `send_started` attempt, appends `ambiguous`, monitoring alerts the operator, and no Scheduler retry can issue a second send.

Alternatives considered:

- Raw CloudFormation: fully capable, but more verbose for Lambda packaging and event configuration.
- Terraform: capable, but adds Terraform state/backend and provider lifecycle management to an AWS-only serverless stack.

Terraform is not used for this change; no Terraform state, backend, provider, or Terraform deployment artifacts are created. AWS SAM and CloudFormation are the sole infrastructure-as-code deployment path.

### Public GitHub repository governance

Keep application source, SAM templates, dependency manifests/lockfiles, workflow definitions, policy configuration, tests, runbooks, and release metadata in one public repository. Establish the public remote and a baseline pull-request validation workflow before continuing MVP implementation. Add an explicit license, README/project metadata, contribution and security policies, code ownership, issue/PR templates, and a code of conduct. After the one documented initial bootstrap push, protect the default branch with pull requests, required checks, authorized review, and stricter ownership for workflow, IAM, OIDC, secret, and release-policy changes. Squash is the repository's only enabled pull-request merge method. All contributors other than the sole maintainer, `@hamdrew`, merge source and policy changes through a squash pull request; the active ruleset grants only `@hamdrew` an audited always-bypass for self-approval, self-merge, and occasional direct default-branch pushes. Enable available Dependabot alerts/security updates, secret scanning/push protection, code scanning, and dependency review.

Alternative considered: keep deployment workflows in a private operations repository. Rejected for this service because public source users need reproducible contribution and release context, and splitting workflow policy from the infrastructure source increases traceability and review friction.

### GitHub Actions CI/CD and AWS authentication

Use separate reusable or clearly scoped workflows for pull-request validation, infrastructure cost/security evidence, deployment, and release publication. Pull-request workflows run formatting, static checks, unit/integration tests, SAM validation/build, dependency/license/vulnerability checks, and the Infracost workflow. Before any deployment workflow, workstation bootstrap procedure, or CI verification stack obtains or uses an AWS apply path, it verifies a current successful or documented authorized-overridden Infracost result for the exact template revision and target environment; absent, stale, malformed, failed, or mismatched evidence fails closed. Template authoring, SAM validation/build, and non-mutating local cost estimation may proceed beforehand. Deployment workflows create the environment-specific CloudFormation change set, retain evidence, and execute only after that gate and the existing dev/staging/prod gates.

Authenticate deployment jobs to AWS through GitHub OIDC. The AWS trust policy is restricted to this repository and approved workflow/ref or GitHub environment claims; GitHub environments isolate `dev`, `staging`, and `prod` variables/secrets, and `prod` requires human approval. Workflow permissions are explicitly minimal. Every GitHub Action reference is pinned to the full commit hash of its latest released version and includes an inline release-tag comment; no action tag, branch, or unannotated commit reference is permitted. The baseline pytest gate enforces 75% line coverage because pytest-cov does not provide a separate branch-only fail threshold. Concurrency cancellation is enabled only for jobs where cancellation cannot leave an external deployment half-applied.

Alternative considered: long-lived AWS access keys in GitHub secrets. Rejected because OIDC provides short-lived credentials and a narrower, auditable trust boundary.

### Dependency updates and release provenance

Configure Dependabot for Python/uv manifests and lockfiles plus GitHub Actions. Dependabot PRs use the ordinary validation and security gates; production/runtime, deployment, and workflow changes retain ownership review. Group only low-risk updates where that does not obscure security or runtime impact.

Use protected semantic-version tags and an authorized release workflow. A release attaches the packaged Lambda artifacts, SBOM, vulnerability/license results, Infracost result, source revision, dependency lock identity, and CloudFormation template/change-set evidence. Sign tags and/or publish verifiable build provenance. Release publication and production deployment remain separate steps: a release identifies the immutable artifact, while the protected production environment authorizes deployment.

Alternative considered: manually upload ZIPs from a developer workstation. Rejected because it breaks reproducibility and release-to-deployment traceability.

### Reproducible Python and image-library packaging

Use Python 3.13 on arm64 for all Lambda functions. Use `uv` to manage the local Python 3.13 toolchain and dependencies: declare direct dependencies in the project package manifest, commit the resolved `uv.lock`, and run `uv sync --locked` for production environments. Pin the `uv` version and Python toolchain version so a rebuild does not silently change the graph; a stale lock is a build failure.

Build ZIP artifacts with `sam build --use-container` and an immutable digest for the matching Python 3.13 arm64 SAM build image. The build container uses the pinned `uv` executable and `uv sync --locked`; Pillow is a direct application dependency in the publisher ZIP, built for the Lambda runtime/architecture inside that container. This keeps JPEG/PNG decoding deterministic without a separately managed layer or a container-image deployment, while tests verify imports and representative decoding under the same build image.

The release pipeline emits an SBOM for the resolved dependency graph and packaged artifact, scans dependencies and the artifact for vulnerabilities and licenses, and stores the evidence with the CloudFormation change set. Configured blocking findings stop promotion; exceptions require an explicit, reviewed expiry and rationale.

The CI workflow also records the commit SHA, workflow run, runner/tool versions, lockfile digest, SAM template digest, and release/tag identity with the evidence. No workflow log, artifact, release asset, or public comment may contain Telegram tokens, AWS credentials, secret values, or environment-specific private identifiers.

### Environment isolation, promotion, and rollback

Deploy one environment-scoped SAM/CloudFormation stack for each of `dev`, `staging`, and `prod` in AWS region `us-east-2` and one AWS account. Stacks are named and tagged from the application and environment (for example, `weather-story-bot-prod`). Every resource carries the mandatory `Application`, `Environment`, and `Owner` tags; `Owner` is the single service owner, Andrew Hoffmann (`@hamdrew`). Tables, buckets, functions, schedules, topics, log groups, roles, exact secret ARNs, channels, and alert recipients are never shared across those stacks. The deployment role is scoped to the selected environment's named/tagged resources. Parameters contain only validated non-secret values: an enumerated environment, its exact pre-created secret ARN, deployment mode, and active-office configuration. Templates derive physical names rather than accepting arbitrary resource identifiers; they reject empty, malformed, cross-environment, and secret-value parameters, and never put secrets in outputs or change sets.

Create one AWS Budget for the application across the account's tagged resources with a $100 monthly limit. Notify the owner at 80% forecasted spend, 100% actual spend, and 120% actual spend; the 120% notification is an escalation and does not automatically delete or disable resources. Review budget attribution by the `Application`, `Environment`, and `Owner` tags monthly.

Dev uses an injected mock for every Telegram message operation, including private alerts; it may use its own credential only for a protected `getMe` check. Staging sends real photo messages and private alerts only through its distinct bot to its dedicated test destinations. Prod has distinct credentials and destinations and is the only environment allowed to publish to the production channel.

Every staging/prod update begins with a CloudFormation change set. No AWS application resource may be created, updated, or deleted until the exact deployment revision and target environment have a current passing Infracost policy result or documented authorized override; this applies equally to the first dev deployment, workstation bootstrap, and CI verification stacks. Before GitHub OIDC deployment is available, a documented, audited bootstrap permits workstation deployments only to dev and staging after that Infracost gate: dev remains mock-only and staging is limited to its dedicated-channel smoke test. Workstation deployment to prod is prohibited. After GitHub OIDC deployment is available, dev/staging execution may be automated after review checks, and prod execution requires the protected GitHub environment's human approval after review. Run drift detection at least monthly and before a production change set; unresolved drift blocks promotion. Use normal CloudFormation create/update rollback behavior, with retain-on-delete and retain-on-replacement protection for DynamoDB and S3. Create or update Scheduler schedules disabled. After deployment, authorize enablement only after the environment's smoke gate: mock delivery in dev, real dedicated-channel photo delivery in staging, and non-publishing configuration/authentication verification in prod.

Infrastructure rollback is not an external-message rollback. If a function ran before a failed deployment or version rollback, disable schedules, consult durable attempt history, and use the existing reconciliation or history-recovery procedure as applicable; never assert that Telegram content was undone. Re-enable only after the chosen roll-forward, function rollback, or recovery action has been validated.

If a release or deployment workflow is compromised or evidence is incomplete, revoke the affected GitHub environment credentials/trust as appropriate, block the release or merge, rotate any exposed secret, and redeploy only from a newly reviewed commit. A GitHub release rollback selects a prior verified artifact; it does not automatically undo external Telegram messages.

### DynamoDB plus S3 as the system of record

Use DynamoDB for one conditionally mutable current-office record per office, one mutable current-story record per canonical identity, append-only publication attempts and transition events, publication decisions, and image metadata. `OFFICE#{office_id}/CURRENT` contains the latest NWS-enriched office/region metadata, active configuration, and managed pinned-message/invite references; conditional updates protect against stale refreshes while allowing current operational facts to evolve. It is not an audit-history record. The current-story record contains the latest source fields, current revision hash, first- and last-seen times, expiration/lifecycle state, current image reference, and Telegram message/publication state. Conditional updates prevent an older source update from replacing newer state. The retained revision hash allows deduplication and in-place edits but is not a source-revision archive. Store the current downloaded image in an encrypted S3 bucket under a deterministic office/story key and retain its location, content type, size, checksum, and source image identifier in the current-story record.

Keep `OFFICE#{office_id}/CURRENT` and current-story records indefinitely, including a story's committed current-image metadata; do not configure TTL or automatic deletion for them. Set the DynamoDB TTL attribute to an epoch-seconds timestamp 30 days after creation or last update for publication attempts, transition events, run results, quarantine records, and alert-fingerprint state. TTL deletion is asynchronous, so consumers must treat records past their TTL as expired even before DynamoDB removes them. Keep committed current image objects indefinitely after story expiration; delete only a replaced image, retain noncurrent versions for 30 days, and expire staging objects after 7 days. A permanent purge of retained office/story records is a manual, authorized and audited operator process, not a runtime function. Enable DynamoDB PITR at its 35-day maximum and configure monthly AWS Backup snapshots retained for one year. Require an on-demand backup before planned destructive migrations or table replacement.

This is a same-Region recovery posture for MVP: S3 cross-Region replication and multi-Region DynamoDB replication are intentionally out of scope. At least quarterly, restore DynamoDB to a new isolated table, reapply configuration that is not restored automatically (including IAM, tags, TTL, PITR, alarms, and other operational settings), validate sampled history against retained S3 image versions/checksums, record the outcome, and remove the exercise resources. For a production recovery, disable schedules, restore to a new table, validate before a controlled runtime configuration cutover, retain the original table for rollback, and re-enable schedules only after validation.

Alternatives considered:

- DynamoDB binary attributes only: simpler, but unsuitable for larger images and less convenient for retrieval/retention controls.
- S3-only history: durable and inexpensive but not suitable for transactional deduplication.

### Seeded office registry, MKX active first

Seed a versioned registry input with every NWS office ID, then retrieve `/offices/{officeId}` for each entry to verify the ID and seed the NWS name and postal address. Geocode that postal address and persist validated latitude/longitude in each `OFFICE#{office_id}/CURRENT` record. A timezone lookup tool derives the IANA timezone from those coordinates. Each current record contains the unique NWS ID, absolute Weather Stories URL, NWS-derived display name, postal address, geocoded coordinates, IANA timezone, Telegram channel ID, and active flag. NWS-enriched fields and active configuration are conditionally refreshed in place; there is no office metadata audit or snapshot family. Inactive records may omit the channel; activation requires a unique configured Telegram channel. The initial deployment activates only `MKX`; each active office gets its own Scheduler-triggered Lambda invocation, so adding an office requires a configured channel, activation, and a schedule rather than changing a multi-office polling loop. `MKX` is the NWS identifier accepted by the live Weather Stories endpoint for the Milwaukee/Sullivan office; `MKE` is not a valid Weather Stories office identifier.

### NWS Weather Stories contract and normalization

Call each office's configured absolute Weather Stories URL with an identifying `User-Agent` and JSON-compatible `Accept` handling. The observed successful response is JSON-LD with a top-level `stories` array. First validate the collection envelope (JSON object, `stories` array, and no unsupported pagination); an invalid envelope fails the entire collection and processes no items. Then validate each item independently before normalization. A malformed item is quarantined while valid siblings continue: store only its run ID, array index, stable validation error code, affected field, and sanitizer-produced bounded summary under a `QUARANTINE#` record; never create a source identity or retain raw item content for it. Normalize valid items' `officeId`, `startTime`, `endTime`, `updateTime`, `title`, `description`, `altText`, `priority`, `order`, and absolute HTTPS `download` URL. Use `(configured office ID, UUID in the final path segment of download)` as the canonical story identity; retain the complete URL as the image source. The same UUID from different offices is never merged and emits a WARNING log naming the colliding offices. Treat the returned array as complete because this endpoint exposes no pagination metadata. Ignore unknown fields.

Classify NWS `404` and other non-`429` `4xx` responses as non-retryable collection failures. For `429`, honor `Retry-After` for one retry only if the delay and request fit before the 60-second reserve; for `5xx`, connection failures, and timeouts, retry once after one second only if it fits. Otherwise record the failed collection for the next scheduled poll. Preserve only HTTP status, stable error class/code, Retry-After, retry decision/ordinal, and a bounded sanitizer-produced summary—not raw `application/problem+json` fields or error bodies. A run with quarantined items and no independent failure is `success_with_quarantined_items`: it returns Lambda success, emits a metric and deduplicated error alert, and retains a quarantined count alongside its other outcomes. Version committed success/error fixtures under the test fixture directory so contract changes are reviewable and replayable.

### Current story state and expiration

Model a story as one mutable record keyed by its stable source identity: the UUID in the NWS `download` URL paired with the office ID. Compute a deterministic revision hash from normalized story fields and image identity/bytes. When that hash changes, conditionally replace the current source fields and current-image metadata while preserving the record's first-seen timestamp, Telegram message reference, and operational publication audit. Do not retain prior source text, prior metadata, or superseded images. Use NWS `endTime` as the expiration boundary. A story omitted before `endTime` remains current, and failed or invalid polls cannot advance deletion or expiration state. At or after `endTime`, mark the record expired while retaining its committed image reference and S3 object indefinitely.

### In-place Telegram revision updates

Store the Telegram chat/message reference and applied revision hash on the current-story record, while keeping the attempt audit separate. New stories create exactly one photo message in the registry entry's office-specific channel: the retained image is the media and the title/story text are the caption. Never send a companion text message. Material revisions before expiration edit that message in place and replace the photo when the current retained image changes; captions omit office IDs and display names. Render the full caption before enforcing Telegram's 1024-character post-entity-parsing photo-caption limit; if it exceeds the limit, retain the maximum prefix that leaves room for `…` and append the Unicode ellipsis. Definitive edit failures retain the prior message reference and publication state for operator investigation; ambiguous edit outcomes alert and prohibit automatic replacement messages, matching the existing duplicate-protection policy. If a changed story is discovered before any successful initial publication, publish its current state normally.

### Pinned office-information message

Provision a separate protected office-info Lambda with no schedule; operators invoke it on demand after office activation or when NWS metadata changes. It queries the NWS office and referenced region resources, obtains or creates the channel invite link, and conditionally updates the managed pinned-message/invite references and refreshed NWS metadata in the environment's `OFFICE#{office_id}/CURRENT` record. It creates one information message or edits that managed message in place, then pins it. It never enters the Weather Story publication-attempt state machine and never creates a second information message when its durable reference or managed marker identifies the existing one.

The message uses explicit Telegram entities and a readable labeled layout: bold NWS office heading; office ID; linked office home; linked Weather Stories URL; region name and linked region home; address; telephone; email; timezone; and channel invite link. It deliberately excludes the registry's geocoded latitude and longitude. Home and Weather Stories links precede contact rows. Missing optional NWS fields are omitted. The office name, ID, office-home URL, Weather Stories URL, and invite link are required. Dev uses a mock operation; staging/prod use their dedicated channels. Invite links and tokens are never logged or placed in CloudFormation outputs. If required data or Telegram management fails, alert and keep that office's schedule disabled until a successful verification.

### Publication-attempt state machine and lease

Keep a mutable current-story record plus immutable publication-attempt records and separate append-only transition events. Each attempt has a unique attempt ID, scheduled-processing run ID, operation type (`create` or `edit`), target revision hash, reservation owner/lease, and, for edits, the existing Telegram chat/message reference. Each attempt uses exactly these states: `reserved`, `send_started`, `published`, `rejected`, `ambiguous`, `confirmed_received`, and `confirmed_not_received`. The current-story record holds the latest deduplication, image, and message state; attempts and transitions remain the audit source of truth for external delivery.

When a story or revision is eligible, DynamoDB conditionally creates a `reserved` create or edit attempt with a short lease and appends a transition event. An unstarted reservation whose lease expires may be reclaimed. Before calling Telegram, the publisher appends the `send_started` transition; this is the one automatic Telegram API call for that reservation. A positive response appends `published` and records the message ID, applied revision hash, operation type, latency, and sanitized response metadata. A definitive pre-acceptance failure appends `rejected`, an error class, and sanitized response metadata. Each permitted retry receives its own new reservation and attempt ID, preserving one call per reservation.

Telegram-only retries use the 14-minute processing deadline and 60-second shutdown reserve within the Lambda's 15-minute timeout. A `429` response with `parameters.retry_after` waits at least the returned number of seconds only when it fits the remaining processing time; otherwise defer the retry to a later scheduled run. Explicit `5xx` Telegram responses with `ok: false` are retried after 1 second then 2 seconds. At most two retry attempts occur for one story revision in one run. Explicit `4xx` responses other than `429` are not retried. Network loss, timeouts, malformed responses, and lost responses are ambiguous and not retried. Every classification, delay, retry ordinal, and retry/defer decision is appended to the attempt audit history.

When the publisher observes a timeout or lost Telegram response, it appends an `ambiguous` transition, emits a structured error for the existing monitor, and prohibits automatic retry even after lease expiry. After a Lambda interruption that prevents that write, the next run detects the stale `send_started` attempt, appends `ambiguous`, and alerts the operator; it does not retry the attempt. The operator invokes a protected reconciliation Lambda (via AWS console or CLI) with the attempt ID and either appends `confirmed_received` when the create or edit is present or `confirmed_not_received` when it is absent. A later scheduled run may create a new reservation only for `confirmed_not_received`; it never creates a replacement message for an ambiguous edit without reconciliation. Every transition event records the prior state, new state, timestamps, lease data, operation type, revision hash, and operator identity/reason when applicable. Store only HTTP status, Telegram error code/description, NWS or Telegram request/correlation IDs, latency, retry-after value, retry ordinal, and retry/defer decision as response metadata; never store credentials, authorization headers, full request payloads, or raw response bodies.

### Bounded poller execution and continuation

Each office invocation uses a 14-minute processing deadline, leaving the final 60 seconds of its 900-second Lambda timeout for outcome persistence and shutdown. Apply request deadlines of 10 seconds for its NWS collection and each Telegram request, 20 seconds for image download, and 15 seconds for S3 upload plus verification. Retrieve that active office's complete collection before selecting work, then process at most 25 eligible story revisions in source `priority` then `order`. Check the remaining budget before starting a story or retry.

There is no queue. If the story cap or processing deadline prevents starting otherwise eligible work, persist an immutable run-level `deferred` outcome with `story_cap` or `run_budget`, rather than attempting it late in the invocation. The next scheduled invocation for that office re-fetches its collection and re-evaluates the story through ordinary deduplication/reservation logic. Persist an immutable run record with exactly one office ID, collection result, elapsed time, `required_work_completed`, bounded failure reasons, per-office counts of discovered, published, edited, skipped, deferred, quarantined, rejected, and ambiguous stories, and an aggregate count object equal to the invocation totals. A run is `success` only when collection succeeds and all selected eligible stories reach successful or explicitly skipped terminal outcomes; `success_with_deferred` when only controlled deferrals remain for unstarted work; `success_with_quarantined_items` when valid stories complete while malformed items are quarantined; and `failed` when collection or required-outcome persistence fails or selected required work ends rejected, ambiguous, or image-invalid without approved terminal handling. The Lambda returns normally after persisting a failed result, unless that persistence fails. Valid empty collections are `success` with zero discovered stories and `required_work_completed=true`; unresolved required failures emit metrics and the existing deduplicated alert.

### Two-phase image retention and reconciliation

Keep image lifecycle separate from the publication state machine. Only retrieve an image over HTTPS from the configured NWS image-host allowlist (initially `weather.gov` and `*.weather.gov`), allow at most three HTTPS redirects that also match that allowlist, and stream it for at most 20 seconds. Stop at 9 MiB rather than buffering an unbounded response. Accept only non-animated JPEG or PNG whose declared content type agrees with its magic bytes. Decode defensively before persistence and reject images over 25 megapixels, with width-plus-height over 10,000, or with an aspect ratio over 20. Compute SHA-256 while streaming. These limits are stricter than Telegram's 10 MB photo ceiling and enforce its dimension and ratio constraints before upload.

Create or update the current-story record with `image_status=image_pending` and no usable object reference. Upload only an accepted image to a deterministic `staging/` S3 key, then verify it with `HeadObject`, checking verified content type, byte size, SHA-256 checksum, and dimensions. After verification, promote it to the deterministic current-image key and conditionally update the current-story record to `image_status=committed` with that key and metadata; Telegram publication is blocked until that commit. Revalidate the committed bytes/checksum and image limits immediately before every Telegram send or edit. A committed current-story record never points at `staging/`.

If Lambda fails after S3 upload but before the DynamoDB commit, the object remains an uncommitted staging object and is not publishable. A partial download, host/redirect policy failure, content-type/magic-byte mismatch, decoder failure, or byte/dimension/ratio limit failure creates an image failure with bounded diagnostics, alerts the operator, and creates no retained reference or Telegram call. A scheduled reconciliation/cleanup step identifies staging objects without committed current-story references and deletes them after 7 days; S3 lifecycle expiration on the staging prefix is a secondary safety net. Deterministic keys make retries idempotent. When a newer image replaces the current image, the former object is deleted; if a committed reference is missing or fails integrity validation, mark the image invalid, alert, and do not publish it.

The image bucket is private: all Block Public Access controls are enabled, ACLs are disabled by `BucketOwnerEnforced`, the bucket policy denies non-TLS requests, and no public bucket/object URL is an output. Use SSE-S3 and versioning. Current image objects remain indefinitely after story expiration; remove noncurrent versions after 30 days. A noncurrent version is never treated as immediately usable by the publisher.

### Unicode-safe Telegram caption formatting and truncation

Construct the one photo caption as title, newline, and story text. If non-empty source `altText` fits in full, append two newlines and `Image description: {altText}` as plain text; omit that optional section if it would exceed the limit. Do not add office identifiers/display names, source links, or issued/updated timestamp fields because the office is identified by its channel and Telegram supplies message timing. Use an explicit Telegram `bold` entity for the title rather than MarkdownV2, HTML, or `parse_mode`; all remaining source content is literal plain text. Build the final caption and entity first, evaluate it against Telegram's 1024-character post-entity-parsing limit, and when necessary truncate the visible title/body text only at Unicode extended grapheme-cluster boundaries while reserving space for `…`. Re-derive the bold entity from the retained final caption using UTF-16 code-unit offsets and lengths. Apply the same deterministic formatter to every photo send and edit path so retries and tests produce identical content and valid entities.

### Private Telegram alerting with SNS/email fallback

The publisher and alert dispatcher are separate Lambda functions. Provision two SNS topics: an alert-trigger topic and a separate fallback topic with an email subscription. CloudWatch metric/composite alarms publish only on state transitions to the alert-trigger topic; application-detected failures publish to the same topic instead of invoking the dispatcher directly. The alert dispatcher is an SNS subscription with an explicit Lambda resource policy and SNS retry configuration.

Before sending, the dispatcher conditionally reads and updates a DynamoDB alert-state record keyed by a versioned fingerprint of severity, workflow, office ID, normalized error class, and—only for story-specific faults—story identity. Run and correlation IDs remain context, not fingerprint inputs. Send the first occurrence immediately; during a four-hour cooldown increment first/last-seen and count without sending; on the first matching event after cooldown, send one aggregated ongoing alert and restart cooldown. Use `critical` for ambiguous Telegram outcomes, `error` for NWS/image/definitive-Telegram/failed-run faults, and metric-only `warning` for controlled deferrals. Render at most 3,500 Unicode grapheme clusters, adding `…` after safe truncation.

The dispatcher reads the bot token from Secrets Manager and sends `sendMessage` to the configured private chat ID. If that send fails, it records the dispatch result, publishes structured failure context once to the fallback topic, and emits logs/metrics. Neither alert-dispatcher nor fallback delivery failures may publish to the alert-trigger topic or create another private Telegram alert. The fallback topic is excluded from the alert-dispatcher's trigger subscription, preventing loops. No SQS queue or event source is introduced.

### Measurable operations and health signals

Publish custom metrics in the `WeatherStoryBot` namespace with only `Environment` and `OfficeId` dimensions. Emit `RunStarted`, `RunSucceeded`, `RunFailed`, `OfficeRetrievalFailed`, `StoriesDiscovered`, `StoriesPublished`, `StoriesEdited`, `ReservationsAmbiguous`, `ImageUploadFailed`, `Telegram429`, and `AlertFallbackUsed` as `Count` metrics, plus `RunDurationMs`, `NwsRequestDurationMs`, `ImageDownloadDurationMs`, and `TelegramRequestDurationMs` as `Milliseconds` metrics. A valid empty collection emits a successful run and `StoriesDiscovered=0`; absence of `RunStarted` is therefore a distinct health signal. Never use story/run/attempt/message IDs or URLs as dimensions.

Each environment gets its own dashboard and alarm set. Dashboards show run health and volume, failure/ambiguity/fallback counts, p50/p90/p99 latency, Lambda duration/max memory, and whether each schedule is enabled. For enabled schedules, alarm on no start for 20 minutes; any failed run or ambiguity in 15 minutes; retrieval or image failure at least twice across two consecutive runs; Telegram 429 in both of two consecutive runs; or any fallback use. Alarm actions are enabled only after the same smoke-gated scheduler enablement step and publish only on CloudWatch state transitions. During intentional schedule disablement, alarm actions are disabled and the dashboard marks the expected maintenance state. DynamoDB fingerprint state still deduplicates application alerts, including when their metrics continue to increment.

### Verification strategy and environment boundaries

Use versioned, sanitized NWS contract fixtures for envelope/item compatibility, pagination rejection, missing and unknown fields, changed revisions, and omitted stories. Use deterministic Telegram fault injection for 429, 5xx, timeout, and accepted-then-lost responses; do not generate rate limits or ambiguous delivery against live staging or production destinations. Staging performs only a successful real photo-delivery smoke test to its dedicated test channel.

Run AWS control-plane verification in a uniquely named ephemeral dev stack. ### IAM role isolation and secret access

SAM/CloudFormation provisions separate publisher, alert-dispatcher, reconciliation, rotation-smoke, office-info, and Scheduler execution roles. A separately documented, pre-created deployment role is trusted only by authorized deployment CI or operators, may pass only those named roles, manages only this application's named/tagged CloudFormation resources, and is never assumed by runtime functions. Runtime trust policies name only their required AWS service principals and use exact resource ARNs and supported conditions; wildcard resources are forbidden unless the AWS action cannot be resource-scoped and a supported condition limits it.

Use one DynamoDB table with explicit partition-key families: `OFFICE#`, `STORY#`, `ATTEMPT#`, `TRANSITION#`, `RUN#`, `QUARANTINE#`, and `ALERT#`. The `OFFICE#` family has only the conditionally mutable `CURRENT` sort-key record; it has no snapshot or audit-record variant. The publisher is restricted to story/run/publication families except `OFFICE#` and `ALERT#`; the office-info manager is restricted to `OFFICE#`; the dispatcher is restricted to `ALERT#`; apply `dynamodb:LeadingKeys` conditions to those prefixes wherever supported. The reconciliation function can read `ATTEMPT#`/`TRANSITION#` and append an authorized reconciliation transition only. None of the runtime roles receives `dynamodb:Scan`.

The publisher may list only the required `staging/` and retained-image prefixes, read/write/copy objects in those prefixes, and delete only `staging/` objects. It reads the exact Telegram secret only at `AWSCURRENT`, publishes only application failures to the alert-trigger SNS topic, and emits its own logs/metrics. The dispatcher reads only `ALERT#` records, reads that same secret only at `AWSCURRENT`, publishes only to the fallback SNS topic, and emits its own logs/metrics. The reconciliation role has no secret, S3, or SNS permission.

The dedicated rotation-smoke Lambda reads the exact secret only at `AWSPENDING`, with `kms:Decrypt` only for the secret's customer-managed key when applicable, and calls Telegram `getMe`. It has no DynamoDB, S3, SNS, or Telegram-message publishing permission. Publisher and dispatcher roles have no `AWSPENDING` access. No runtime role may list, write, rotate, or access another secret. The pre-created secret uses the JSON shape `{"schema_version":1,"telegram_bot_token":"…"}`; templates reference only its exact ARN, and channel/alert-recipient IDs remain non-secret configuration.

The Scheduler execution role trusts only `scheduler.amazonaws.com` and invokes only the qualified publisher Lambda ARN. Bind its trust and invoke permissions to this account and application's office schedules with `aws:SourceAccount` and `aws:SourceArn` conditions where supported. At runtime, publisher and dispatcher explicitly request `AWSCURRENT`, validate the JSON schema, and cache the parsed token for at most 60 seconds. The operator rotates manually because BotFather creates the replacement token: write it as `AWSPENDING`, invoke the protected dedicated `getMe` smoke Lambda, move it to `AWSCURRENT`, wait through the cache TTL, and invoke the normal runtime smoke test. Retain `AWSPREVIOUS` only for rollback/forensics; if smoke testing fails, restore that label to the known-good version and repeat the runtime test. Redact the token and token-bearing Telegram URLs from all logs, traces, errors, alert content, persisted metadata, and test fixtures.

### Allowlisted CloudWatch logging and redaction

All Lambda log emission passes through one structured-log sanitizer. Its schema permits only event timestamp, log level, event type, component, `office_id`, `run_id`, `attempt_id`, revision hash, outcome/status, HTTP status, stable error class/code, a sanitizer-produced error summary capped at 256 characters, latency, retry ordinal, retry/defer decision, and aggregate outcome counts. Event-specific fields are optional, but no arbitrary context map is permitted. The sanitizer never serializes raw or token-bearing URLs, Telegram chat/message IDs, story IDs, S3 keys, story text/title/description/alt text/image metadata, secret values, headers, request/response bodies, raw exceptions, stack traces, or unbounded upstream error text.

Use a validated non-secret environment-scoped `log_level` of `DEBUG`, `INFO`, `WARNING`, or `ERROR`. Dev and staging default to `DEBUG`; prod defaults to `INFO` and rejects `DEBUG`. DEBUG enables additional sanitized lifecycle and decision events, including request start/completion and latency, validation stage and stable code, retry-budget decisions, and deduplication/reservation decisions. It never widens the allowlist or permits raw tracing, arbitrary context, or sensitive data.

Sensitive operational identifiers are omitted, not hashed: a hash would support correlation but not authorized recovery, while logged `run_id`, `attempt_id`, and revision hash already provide the path to the protected DynamoDB/S3 history when an investigation needs raw values. Configure every publisher, alert-dispatcher, reconciliation, and rotation-smoke Lambda CloudWatch Logs group with 90-day retention. Logs are diagnostic signals, not the durable audit source of truth.

## Risks / Trade-offs

- [Telegram outcome is ambiguous after a timeout] → Transition the attempt to `ambiguous`, alert the operator, and require explicit reconciliation rather than risking a duplicate post.
- [Image storage increases retention cost] → Apply lifecycle/retention settings and store only the images required by discovered stories.
- [NWS schema or availability changes] → Validate response shape, emit structured errors and alerts, and preserve failed attempt details per office.
- [Telegram rate limits or media constraints] → Process stories sequentially, enforce message limits before sending, capture response errors, and retry only definitive pre-acceptance failures.
- [Private alert and SNS/email fallback both fail] → Emit structured CloudWatch logs/metrics for the failure and retain the failed alert context for investigation.
